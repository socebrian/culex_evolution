# Population genomics of Culex pipiens from Southwestern Spain
## Part 1.5: Running BITACORA: Cx pipipens
### Sonia Cebrian-Camison scebrian27@gmail.com/sonia.cebrian@ebd.csic.es

Issues Encountered When Running BITACORA with the First Culex pipiens Genome (EviAnn Annotation made by us)

When I attempted to run BITACORA in full mode using the Culex pipiens EviAnn annotation, I encountered several problems that required multiple rounds of debugging. Below I describe the full sequence of issues and how I resolved them.

### 1. Initial warning: multiple isoforms and overlapping CDS
*Warning: The input GFF contains coding sequences in overlapping positions (such as isoforms).*

This indicated that the EviAnn GFF contained multiple isoforms per gene. Although this warning does not stop the run, it is not ideal for comparative genomic analyses, so I decided that I would work with one isoform per gene.

I tried AGAT and successfully ran:
```bash
agat_sp_keep_longest_isoform.pl \
    -gff culexPipiens.eviann_annotation.gff3 \
    -o culexPipiens.eviann_annotation_longest.gff3
```
I regenerated the proteome from this new GFF:
```bash
conda install bioconda::agat 
perl Scripts/gff2fasta_v3.pl \
     culexPipiens.softmasked.fasta \
     culexPipiens.eviann_annotation_longest.gff3 \
     culexPPipiens_longest
```

After this, I tried BITACORA again using the “longest-isoform” GFF and FASTA.

### 2. Hard error: many protein IDs not found in the GFF
BITACORA consistently stopped at the step where it checks that every protein ID in the FASTA corresponds to an mRNA entry in the GFF. Errors looked like:

*ERROR in Scripts/check_data.pl: Protein gene LOC_00000001-mRNA-1 is not found in the GFF3*

To diagnose this, I ran BITACORA’s helper script:
```bash
perl Scripts/Tools/get_proteins_notfound_ingff.pl \
     culexPipiens.eviann_annotation.gff3 \
     culexPPipiens.pep.fasta
``` 
None of the proteins were found in the fasta file. 


### 3. A false lead: trying to simplify protein IDs
At first I suspected that the ID format might be causing BITACORA to fail. For example:
GFF mRNA IDs looked like:
ID=LOC_00000002-mRNA-1,Class;Parent=LOC_00000002
FASTA headers looked like:
>LOC_00000002-mRNA-1

I tried normalizing the protein IDs by removing everything after the gene identifier:
```bash
sed '/^>/ s/-.*//' culexPPipiens_longest.pep.fasta \
    > culexPPipiens_longest_gene.pep.fasta
```
However, stripping the isoform suffix actually made things worse, because BITACORA expects FASTA headers to match mRNA/transcript IDs, not gene IDs. I reverted this modification.

### 5. Identifying the actual issue: EviAnn adds a “,Class” suffix to mRNA IDs
After checking several problematic entries manually, we realised the real problem: **In the EviAnn annotation, many mRNA IDs contain an unexpected suffix: ID=LOC_00011661-mRNA-1,Class;**
The “,Class” part breaks BITACORA’s internal ID matching logic, because BITACORA expects clean IDs without commas. This formatting issue affected only the mRNA IDs but not the gene IDs or CDS IDs, which explains why the mismatch was systematic.

I removed all occurrences of “,Class” from the GFF:
```bash
sed 's/,Class//g' culexPipiens.eviann_annotation_longest.gff3 \
    > culexPipiens.eviann_annotation_longest_reformat.gff3
```
Since I verified that “Class” did not appear elsewhere in the GFF, this operation was safe.

After cleaning the GFF:
* I kept the protein headers with the -mRNA-1 suffix (as required by BITACORA).
* I re-ran BITACORA using:
GFF = culexPipiens.eviann_annotation_longest_reformat.gff3
PROT = culexPPipiens_longest.pep.fasta
BITACORA now parsed the files correctly and started the analysis without further ID-related errors.
